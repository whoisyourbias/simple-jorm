사용법에서 한 걸음, 실행 원리로.

어노테이션은 실행 코드가 아닙니다. 프레임워크가 읽는 메타데이터이며, 그 뒤에는 연결·SQL·객체 상태를 처리하는 코드가 있습니다.

JDBC는 DB 연결 API, Spring JDBC는 반복 실행 절차, MyBatis는 SQL과 메서드·결과의 매핑을 맡습니다. JPA는 객체 영속화 표준이며 Hibernate ORM은 그 구현체입니다. Spring 트랜잭션은 여러 작업의 성공과 실패를 하나의 경계로 묶습니다.

읽는 법. 단계별 질문과 코드, 실행 그림을 차례로 보세요. 예제는 전제 조건을 줄인 교육용 코드입니다. 내부 흐름의 의사 코드는 실제 라이브러리 소스와 구분해 표시하고, 단계 끝에서 공식 문서와 소스로 연결합니다.
01
SPRING JDBC · 실행과 행 매핑

SQL은 다르지만, 실행은 비슷하다.

사용자 한 명을 조회할 때마다 연결을 얻고, 문장을 준비하고, 값을 넣고, 결과를 읽고, 자원을 닫습니다. SQL이 바뀌어도 이 과정은 반복됩니다.

“바뀌는 SQL과, 바뀌지 않는 실행 절차를 나눌 수 없을까?”

직접 JDBC · 실행과 변환을 함께 작성
try (Connection c = source.getConnection();
     PreparedStatement ps = c.prepareStatement(
       "SELECT id, name FROM users WHERE id = ?")) {
  ps.setLong(1, 1L);
  try (ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
      // 결과 한 행을 User로 변환
    }
  }
}
Spring JdbcTemplate · 콜백으로 한 행 변환
JdbcTemplate jdbc = new JdbcTemplate(source);
User user = jdbc.queryForObject(
  "SELECT id, name FROM users WHERE id = ?",
  (rs, rowNum) -> {
    User u = new User();
    u.setId(rs.getLong("id"));
    u.setName(rs.getString("name"));
    return u;
  }, 1L
);
JdbcTemplate→DataSourceUtils · Connection→PreparedStatement · ResultSet→RowMapper → User
EXECUTION

템플릿은 자원과 예외를 관리한다.

JdbcTemplate이 SQL 실행, ResultSet 반복, 문장과 결과의 정리를 맡습니다. DataSourceUtils를 통해 Spring 트랜잭션에 묶인 연결을 재사용하고, 그 연결의 실제 종료는 트랜잭션 경계까지 미룹니다.

JDBC의 checked SQLException은 SQLExceptionTranslator가 unchecked DataAccessException 계층으로 바꿉니다.

MAPPING

BeanPropertyRowMapper는 setter로 쓴다.

기본 생성자로 객체를 만들고 컬럼 라벨을 public setter의 프로퍼티명에 연결합니다. first_name은 setFirstName(...)과 연결됩니다. 필드에 직접 쓰는 매퍼로 이해하면 안 됩니다.

BeanWrapper와 ConversionService가 JDBC 값과 프로퍼티 타입을 연결합니다. 기본 변환 서비스는 Java 시간 타입 등도 처리하며, 사용자 변환 서비스도 지정할 수 있습니다.

단건 조회는 “정확히 한 행”이라는 계약이다.

queryForObject는 0행이면 EmptyResultDataAccessException, 여러 행이면 IncorrectResultSizeDataAccessException을 던집니다. 한 행의 SQL NULL이나 매퍼 반환값이 null인 경우와 “결과 행이 없음”은 다릅니다.

이름·NULL·생성자를 확인하세요

이름이 다르면 SELECT fname AS first_name ...처럼 별칭을 사용합니다. BeanPropertyRowMapper는 JPA의 @Column을 해석하는 매퍼가 아닙니다.

DB NULL을 primitive setter에 넣으면 기본적으로 타입 오류입니다. primitivesDefaultedForNullValue로 해당 대입을 무시할 수 있습니다. record나 생성자 기반 객체는 DataClassRowMapper를 살펴보세요.

02
MYBATIS · SQL 매핑과 프록시

메서드를 호출했는데, SQL이 실행된다.

호출자는 findById(1L)만 호출합니다. MyBatis는 Mapper 인터페이스와 등록된 SQL을 연결하고, JDBC 결과를 객체로 매핑합니다.

MyBatis · org.apache.ibatis.annotations
public interface UserMapper {
  @Select("SELECT id, name FROM users WHERE id = #{id}")
  User findById(@Param("id") Long id);

  default User first() {
    return findById(1L);
  }
}

// 열린 SqlSession의 수명은 호출 측에서 관리
UserMapper mapper = session.getMapper(UserMapper.class);
User user = mapper.findById(1L);
CONFIGURATION → EXECUTION

선언은 등록할 때, 호출은 실행할 때.

XML이나 @Select 같은 선언은 설정 분석 과정에서 MappedStatement로 등록됩니다. 호출할 때마다 단순히 어노테이션에서 SQL 문자열을 꺼내 실행하는 구조가 아닙니다.

SqlSession.getMapper()가 돌려주는 JDK 프록시에는 MapperProxy가 연결됩니다. 호출은 캐시된 메서드 실행기에서 MapperMethod를 거쳐 SqlSession으로 전달됩니다.

MapperProxy→캐시된 메서드 실행기→SqlSession → Executor→JDBC → ResultMap·TypeHandler
Mapper와 RowMapper를 구분하세요. MyBatis Mapper는 SQL 호출 인터페이스입니다. Spring의 RowMapper는 JDBC 결과 한 행의 변환 콜백입니다. MyBatis는 Spring JdbcTemplate을 거치지 않고 자체 Executor·StatementHandler·ResultSetHandler 경로를 사용합니다.
이름 바인딩 · SQL의 순서와 인자 순서는 다를 수 있다
@Select("SELECT id, name FROM users " +
        "WHERE name = #{name} AND id = #{id}")
User find(@Param("id") Long id,
          @Param("name") String name);

// SQL: ... WHERE name = ? AND id = ?
// 바인딩 값: ["Alice", 1L]
mapper.find(1L, "Alice");
PARAMETERS & DEFAULT METHODS

이름은 파라미터를, default는 본문을 찾는다.

@Param은 인자의 명시적 이름을 만듭니다. #{id}는 JDBC 파라미터가 되고 TypeHandler가 값을 바인딩합니다. bean 속성이나 여러 파라미터도 매핑할 수 있습니다. ${...}는 문자열 치환이므로 사용자 입력을 그대로 넣으면 SQL 삽입 위험이 있습니다.

default 메서드는 DefaultMethodInvoker의 MethodHandle로 본문을 실행합니다. 본문에서 다른 Mapper 메서드를 호출하면 프록시로 재진입합니다.

INTERACTIVE / MYBATIS MAPPER PROXY

호출 한 번을, 끝까지 따라가 보기.

MyBatis의 실제 계층을 따라 ① 인자 · ② SQL · ③ 결과를 추적합니다. 캐시 적중이 없는 단순 조회를 가정합니다.

JavaScript 없이도 아래 전체 실행 순서를 읽을 수 있습니다.
전체 실행 순서 · 정적으로 읽기
  1. XML 또는 @Select를 분석해 MappedStatement를 등록합니다.
  2. SqlSession.getMapper()가 MapperProxy를 연결한 프록시를 반환합니다.
  3. findById(1L)은 cachedInvoker(method)를 통해 메서드 실행기로 전달됩니다.
  4. MapperMethod가 @Param 이름과 반환 타입에 맞춰 SqlSession.selectOne()을 호출합니다.
  5. Executor와 문장 처리기가 JDBC 실행을 준비하고, TypeHandler가 값을 바인딩합니다.
  6. 결과 처리기가 ResultMap과 TypeHandler로 행을 객체에 매핑하고 반환합니다.

XML·어노테이션 어디에도 등록된 SQL이 없는 추상 메서드는 BindingException으로 실패합니다. 어노테이션이 없어도 XML 매핑이 있으면 실행할 수 있습니다. Object 메서드는 MapperProxy 자신에게 위임하며, default는 별도 본문 실행 경로를 사용합니다.

공식 문서·소스를 바탕으로 계층을 생략한 교육용 시각화입니다. 표시 코드는 설명용 의사 코드이며 Java·DB를 브라우저에서 실행하지 않습니다.
결과 매핑과 단건 반환은 어떻게 결정될까?

ResultMap은 컬럼과 객체 프로퍼티·생성자·연관 결과의 매핑을 표현하고, TypeHandler는 Java와 JDBC 타입 사이의 값을 처리합니다. 자동 매핑도 설정할 수 있으며 mapUnderscoreToCamelCase는 기본 false입니다.

selectOne은 0행이면 null, 2행 이상이면 TooManyResultsException입니다. Spring JDBC의 단건 조회와 계약이 다릅니다. 지연 로딩·캐시·플러그인이 있으면 실제 실행 경로와 SQL 시점도 달라질 수 있습니다.

프록시의 toString()은 MapperProxy의 Object 메서드를 호출한 결과입니다. 고정 문자열이나 SQL 조회 결과가 아닙니다.

03
SPRING TRANSACTIONS · 프록시와 자원 경계

두 번의 SQL, 하나의 성공.

출금은 성공했는데 입금이 실패했습니다. 각각 확정되면 업무 일부만 반영됩니다. Spring의 선언적 트랜잭션은 프록시를 통과하는 업무 호출에 시작과 종료 경계를 더합니다.

Spring · 선언적 경계와 JdbcTemplate
// Spring이 관리하는 Service bean의 메서드
@Transactional
public void transfer() {
  jdbc.update("UPDATE accounts SET balance = balance - ?"
      + " WHERE id = ?", 30, 1L);
  jdbc.update("UPDATE accounts SET balance = balance + ?"
      + " WHERE id = ?", 30, 2L);
}
// 같은 DataSource의 DataSourceTransactionManager 사용
// JDBC 제약 위반 → DataAccessException → 기본 롤백
THREAD-BOUND RESOURCES

인터셉터는 경계를, 관리자는 자원을 맡는다.

Spring AOP 프록시의 TransactionInterceptor가 트랜잭션 속성을 해석하고 PlatformTransactionManager를 호출합니다. JDBC에서는 DataSourceTransactionManager가 연결을 현재 스레드에 묶습니다.

JdbcTemplate은 같은 DataSource의 thread-bound connection을 얻습니다. 새로운 트랜잭션이면 autoCommit을 끄고, 종료 시 commit 또는 rollback 뒤 자원을 해제합니다. 새 스레드로 자동 전파되지는 않습니다.

Spring AOP 프록시→TransactionInterceptor→트랜잭션 관리자→Service → 같은 연결의 SQL

예외가 발생했다고 항상 롤백하지는 않는다.

기본 설정은 RuntimeException·Error 롤백, checked 예외는 커밋입니다. 예외는 호출자에게 계속 전달됩니다. checked 업무 예외도 롤백하려면 @Transactional(rollbackFor = BusinessException.class)로 지정합니다. noRollbackFor는 지정 예외의 롤백을 제외하며, 가장 구체적인 일치 규칙이 우선합니다.

Spring JDBC의 DataAccessException은 RuntimeException이므로 기본 롤백 대상입니다. 직접 JDBC에서 던진 checked SQLException의 기본 정책과 혼동하지 마세요. Spring 6.2부터는 전역 기본 롤백 정책을 변경하는 설정도 있으므로 여기서는 변경하지 않은 기본 설정을 가정합니다.

INTERACTIVE / SPRING PROXY BOUNDARY

같은 실패인데, 잔액이 다르다?

두 계좌는 100에서 시작합니다. 출금 30은 성공하고, 입금은 상한 120 제약으로 실패합니다. Spring JdbcTemplate의 DataAccessException이 호출자까지 전파되며 기본 롤백 규칙이 적용됩니다. 트랜잭션이 없으면 autoCommit=true인 연결을 가정합니다.

JavaScript 없이도 아래 전체 실행 순서를 읽을 수 있습니다.
전체 실행 순서 · 정적으로 읽기
  1. 외부 → transfer: 프록시가 경계를 시작합니다. 출금까지 롤백하여 최종 잔액은 100 / 100입니다.
  2. 비트랜잭션 바깥 → this.transfer: target 내부 호출은 프록시를 다시 통과하지 않습니다. 출금은 자동 커밋되어 70 / 100이 남습니다.
  3. 트랜잭션 바깥 → this.transfer: 자기 호출은 새 경계를 만들지 않지만 기존 트랜잭션은 유지됩니다. 바깥 경계로 실패가 전파되어 100 / 100으로 롤백됩니다.

프록시 기반 AOP 모드의 동작입니다. 중간 잔액은 작업 효과를 나타내며, 다른 연결에 미커밋 데이터가 보인다는 의미가 아닙니다.

공식 문서·소스를 바탕으로 계층을 생략한 교육용 시각화입니다. 표시 코드는 설명용 의사 코드이며 Java·DB를 브라우저에서 실행하지 않습니다.
REQUIRED와 rollbackOnly · 안쪽 예외를 잡아도 왜 실패할까?

REQUIRED는 기존 트랜잭션이 없으면 시작하고, 있으면 같은 물리 트랜잭션에 참여합니다. 참여한 프록시 경계를 롤백 대상 예외가 넘어가면 rollbackOnly를 표시할 수 있습니다. 바깥에서 예외를 잡아도 이 표시가 남으면 커밋할 수 없어 UnexpectedRollbackException이 발생합니다.

같은 메서드 안에서 예외를 잡아 인터셉터에 전달하지 않으면 인터셉터의 예외 기반 롤백 판단은 실행되지 않습니다. DB나 JPA provider가 자원 자체를 rollback-only로 만든 경우는 별도입니다. 자기 호출의 내부 어노테이션은 새로운 참여 경계로 해석되지 않습니다.

REQUIRES_NEW는 별도 물리 트랜잭션, NESTED는 보통 JDBC savepoint를 이용합니다. 실제 지원은 선택한 관리자와 자원에 달려 있습니다.

04
JPA / HIBERNATE · 구조와 매핑 메타데이터

객체 구조가 SQL의 재료가 된다.

Jakarta Persistence(JPA)는 객체 영속화의 표준 API와 매핑 규칙입니다. Hibernate ORM은 이를 구현하는 provider이며, 메타데이터를 분석해 SQL과 객체 사이를 연결합니다.

jakarta.persistence · 필드 접근 매핑
@MappedSuperclass
abstract class BaseEntity {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  protected Long id;
}

@Entity
@Table(name = "users")
class User extends BaseEntity {
  @Column(name = "user_name")
  String name;
  @Transient
  String displayLabel;
  protected User() {}

매핑 메타데이터→provider의 엔티티·SQL 처리→JDBC→DB

provider는 클래스·속성·테이블·컬럼·식별자·연관관계의 매핑을 구성합니다. @Entity가 엔티티를 선언하고 @Table은 테이블을 지정합니다. ID를 필드에 두면 기본적으로 필드 접근, getter에 두면 프로퍼티 접근을 사용하며 @Access로 명시할 수 있습니다.

INHERITANCE

상속은 매핑 모델의 선택이다.

@MappedSuperclass의 매핑 속성은 하위 엔티티로 상속됩니다. 상위 타입 자체는 엔티티나 독립 조회 대상이 아니며 전용 테이블을 만들지 않습니다.

엔티티 상속은 @Inheritance로 SINGLE_TABLE·JOINED·TABLE_PER_CLASS 전략을 선택합니다. 엔티티 계층의 기본은 SINGLE_TABLE이며, 일반 비엔티티 상위 클래스의 상태는 자동으로 영속 매핑되지 않습니다.

PERSISTENT ATTRIBUTES

저장할 상태를 명시한다.

필드 접근에서는 static·Java transient·@Transient 필드를 영속 상태에서 제외합니다. 프로퍼티 접근이면 매핑 대상 getter에 @Transient를 둡니다.

@Column(insertable = false, updatable = false)는 INSERT·UPDATE SQL 참여를 제어합니다. 조회 매핑도 제외하는 @Transient와 의미가 다릅니다.

식별자 전략과 INSERT 시점

직접 지정 ID와 @GeneratedValue를 구분합니다. IDENTITY는 DB INSERT로 생성되는 키, SEQUENCE는 DB 시퀀스, TABLE은 키 생성 테이블, UUID는 UUID 생성, AUTO는 provider가 선택하는 전략입니다. 지원과 최적의 선택은 DB·provider에 따라 달라집니다.

persist()의 의미는 새 엔티티를 관리 상태로 만드는 것입니다. 언제나 flush까지 INSERT를 미루는 API는 아닙니다. Hibernate의 GenerationType.IDENTITY는 생성 키를 얻기 위해 persist 시 즉시 INSERT가 필요할 수 있습니다. SQL 실행과 트랜잭션 커밋은 별개입니다.

MyBatis → SqlSession → Executor개발자가 작성한 SQL 중심
JPA → Hibernate ORM매핑과 관리 상태 중심
각자의 실행 계층 → JDBC 드라이버 → DB

Hibernate가 MyBatis나 Spring JdbcTemplate을 거치는 구조는 아닙니다. Spring과 함께 쓰면 선택한 트랜잭션 관리자와 자원 설정에 따라 경계를 통합합니다.

같은 객체를 기억하고, 변경을 동기화한다.

영속성 컨텍스트는 엔티티의 관리 공간입니다. 동일한 영속성 식별자를 한 객체로 다루고, 관리 중인 상태를 DB에 동기화합니다. 매핑 메타데이터 캐시와는 역할이 다릅니다.

MANAGED STATE

관리하는 객체의 변경을 찾는다.

Hibernate의 일반적인 dirty checking은 로딩 당시 스냅샷과 현재 상태를 비교합니다. 변경된 관리 엔티티에 필요한 UPDATE를 flush 과정에서 준비합니다. 바이트코드 향상 등으로 변경 추적 방법을 최적화할 수도 있습니다.

JPA는 변경 동기화의 의미를 규정하며 특정 스냅샷 알고리즘을 의무화하지 않습니다. 모든 Java 객체가 대상은 아닙니다. 새 객체는 persist, 분리된 객체는 merge 등으로 관리 상태와 연결해야 합니다.

관리 엔티티 수정→dirty checking→flush · SQL 실행→commit · 트랜잭션 확정

flush는 동기화, commit은 확정이다.

flush()는 현재 영속성 컨텍스트의 변경을 DB에 보냅니다. 트랜잭션을 끝내지 않으므로 이후 rollback으로 취소할 수 있습니다. commit은 트랜잭션을 확정하며 보통 그 전에 필요한 flush가 수행됩니다.

FlushModeType.AUTO에서는 트랜잭션 커밋 전뿐 아니라 쿼리 결과에 영향을 줄 변경이 있으면 쿼리 실행 전에도 동기화가 필요할 수 있습니다. Hibernate는 JPQL/HQL의 관련 테이블, native SQL의 실행 API와 동기화 설정 등을 보고 시점을 판단합니다. 모든 쿼리 직전에 무조건 전체 UPDATE를 보내는 것은 아닙니다.

COMMIT 모드 · clear · rollback 이후

FlushModeType.COMMIT은 커밋 시 동기화를 중심으로 하며 쿼리에 대한 미반영 변경의 영향은 표준상 지정되지 않습니다. 실제 flush는 활성 트랜잭션과 컨텍스트의 트랜잭션 참여 조건도 확인해야 합니다.

clear()는 관리 엔티티를 분리하므로 flush하지 않은 변경을 잃을 수 있습니다. rollback이 Java 객체의 필드 값을 예전 값으로 복원하는 것은 아닙니다. 예외나 rollback 이후에는 컨텍스트 수명과 재조회 전략을 함께 관리해야 합니다.

편해진 매핑에는 어떤 비용이 있을까?

편리한 자동 매핑과 직접 작성한 변환은 준비 과정과 실행 비용이 다를 수 있습니다. 성능을 비교할 때는 측정 범위부터 확인해야 합니다.

WHAT TO MEASURE

실제 업무 경로를 측정한다.

행 변환만 측정할 때와 SQL 실행·네트워크·트랜잭션까지 포함할 때 결과는 다릅니다. 행 수·컬럼 수·타입 변환·메타데이터 재사용·워밍업도 영향을 줍니다.
