먼저, 이 프로젝트의 위치

사용법보다, 동작하는 이유.

“어노테이션 하나면 된다”의 안쪽에는 누군가 작성한 실행 코드가 있습니다. 이 프로젝트는 그 역할을 작은 단위로 직접 구현한 학습용 라이브러리입니다.

Spring이나 Hibernate를 프로덕션 코드에서 호출하지 않고 JDBC·리플렉션·JDK 동적 프록시를 사용합니다. 여기서 만든 EntityManager는 자체 API이며 JPA 표준 구현체는 아닙니다. 아래의 기술 대응은 비슷한 역할을 배운다는 의미입니다.

읽는 법. 각 단계의 질문부터 읽고, 실행 그림과 짧은 코드를 확인하세요. 주황색 비교 상자에는 실제 라이브러리와의 차이를, 단계 끝에는 아직 해결하지 못한 문제를 적었습니다.
01
1 / 5 · 먼저 알 것: SQL, 객체, 메서드 구현 완료

SQL은 다르지만, 실행은 비슷하다.

사용자 한 명을 조회할 때마다 연결을 얻고, 문장을 준비하고, 값을 넣고, 결과를 읽고, 자원을 닫습니다. SQL이 바뀌어도 이 과정은 반복됩니다.

“바뀌는 SQL과, 바뀌지 않는 실행 절차를 나눌 수 없을까?”

BEFORE · 직접 JDBC — 설명용 축약
try (Connection c = source.getConnection();
     PreparedStatement ps = c.prepareStatement(
       "SELECT id, name FROM users WHERE id = ?")) {
  ps.setObject(1, 1L);
  try (ResultSet rs = ps.executeQuery()) {
    if (rs.next()) {
      User user = new User();
      user.id = rs.getLong("id");
      user.name = rs.getString("name");
    }
  }
}
AFTER · 실행과 한 행 변환 분리
User user = jdbc.queryForObject(
  "SELECT id, name FROM users WHERE id = ?",
  (rs, rowNum) -> {
    User u = new User();
    u.id = rs.getLong("id");
    u.name = rs.getString("name");
    return u;
  },
  1L
);

SQL과 변환 방법을 넘기면 나머지는 템플릿이 처리합니다.

호출 코드→JdbcTemplate→Connection · PreparedStatement→ResultSet→RowMapper → User
EXECUTION

템플릿은 실행 절차를 맡는다.

JdbcTemplate이 연결 획득, ?의 순서별 바인딩, 실행과 자원 정리를 맡습니다. 조회 시 커서를 다음 행으로 이동시키는 것도 템플릿의 책임입니다.

MAPPING

매퍼는 한 행을 객체로 바꾼다.

RowMapper는 변환 콜백입니다. 자동 매퍼는 기본 생성자와 필드를 찾아두고, 조회별 prepare()에서 컬럼 순서에 맞는 필드 배열을 준비해 재사용합니다.

실제 Spring JDBC와 어디가 다를까?

반복 실행을 템플릿에 모은다는 역할은 같습니다. 자체 구현은 SQLException을 전달하지만 Spring은 이를 DataAccessException 계층으로 변환합니다. 자체 단건 조회는 결과가 없으면 null, 여러 행이면 첫 행을 반환합니다. Spring의 일반적인 queryForObject는 정확히 한 행을 요구합니다.

자체 자동 매퍼는 필드에 직접 대입하고 별도 타입 변환·상속 필드 매핑을 지원하지 않습니다. Spring의 동명 매퍼는 JavaBean 프로퍼티와 변환 기능을 사용합니다. 이름이 같아도 같은 구현은 아닙니다.

자동 매핑에서 이름이 중요한 이유

이 단계의 BeanPropertyRowMapper는 컬럼 라벨과 필드명을 대소문자 구분 없이 연결합니다. user_name을 name 필드에 넣으려면 SELECT user_name AS name ...처럼 별칭을 사용합니다. 엔티티 단계의 자체 @Column은 여기서 해석하지 않습니다.

조회 결과가 비어 있으면 목록 조회는 빈 리스트를 반환합니다. update()는 INSERT·UPDATE·DELETE의 변경 행 수를 반환합니다.

메서드를 호출했는데, SQL이 실행된다.

호출자는 findById(1L)만 호출합니다. SQL과 실행 방식은 Mapper 인터페이스 뒤로 옮겼습니다. 그런데 그 인터페이스의 구현 클래스는 직접 작성하지 않았습니다.

선언 · com.jorm.mapper.Select
public interface UserMapper {
  @Select("SELECT id, name FROM users WHERE id = ?")
  User findById(Long id) throws SQLException;
}

UserMapper mapper = MapperFactory.create(
  UserMapper.class, jdbc
);
User user = mapper.findById(1L);
THE MISSING IMPLEMENTATION

구현 객체를 JDK가 만든다.

JDK 동적 프록시는 지정한 인터페이스를 구현하는 객체를 런타임에 만듭니다. 메서드 호출은 연결해 둔 InvocationHandler의 invoke()로 전달됩니다.

핸들러 안의 직접 작성한 코드가 어노테이션을 읽고 JDBC 실행기로 연결합니다. 어노테이션 자체가 SQL을 실행하는 것은 아닙니다.

세 단어를 먼저 구분하세요. UserMapper.class는 인터페이스 타입 정보, mapper는 생성된 프록시 객체, handler는 호출을 해석하고 실행하는 객체입니다. Mapper는 SQL 호출 인터페이스, RowMapper는 결과 한 행의 변환 콜백입니다.
INTERACTIVE 01 / JDK DYNAMIC PROXY

호출 한 번을, 끝까지 따라가 보기.

simple-jorm의 실제 코드 흐름을 재구성한 교육용 시각화입니다. Java나 DB를 브라우저에서 실행하지 않습니다.

JavaScript 없이도 아래 ‘전체 실행 순서’를 읽을 수 있습니다.
전체 실행 순서 · 정적으로 읽기
  1. @Retention(RUNTIME)으로 어노테이션 정보가 클래스 파일에 남고 실행 중 리플렉션으로 읽힙니다.
  2. 팩토리가 클래스 로더, 인터페이스 배열, 핸들러를 Proxy.newProxyInstance()에 전달합니다.
  3. JDK는 프록시 클래스를 생성하거나 재사용하고, 핸들러가 연결된 새 프록시 객체를 만듭니다.
  4. mapper.findById(1L)이 invoke(proxy, method, args)로 전달됩니다.
  5. 핸들러가 인터페이스 메서드의 @Select를 읽고 SQL을 꺼냅니다.
  6. JdbcTemplate이 args[0]을 첫 번째 ?에 바인딩해 SQL을 실행합니다.
  7. BeanPropertyRowMapper가 결과 행을 새 User 객체로 바꿉니다.
  8. 객체가 핸들러와 프록시를 거쳐 호출자에게 반환됩니다.

어노테이션이 없으면 UnsupportedOperationException이 발생합니다. toString()은 SQL 검사보다 먼저 별도로 처리하여 "MapperProxy"를 반환합니다.

① 호출 인자 · ② SQL · ③ 결과 객체를 같은 이름표로 추적하세요. 처음에는 ‘다음’ 버튼으로 한 장면씩 읽는 것을 권합니다.
RUNTIME이 없으면? · 생성된 프록시는 어떻게 생겼을까?

SOURCE는 컴파일 때 버려지고, CLASS는 클래스 파일에 기록되지만 런타임 리플렉션 조회를 보장하지 않습니다. RUNTIME이 실행 중 조회를 가능하게 합니다. 이 프로젝트의 처리는 컴파일 타임 어노테이션 프로세서가 아닙니다.

아래는 개념을 설명하는 의사 코드입니다. 실제 생성 클래스 이름과 바이트코드, 예외 처리 코드는 JDK에 따라 달라질 수 있습니다.

설명용 의사 코드 · 실제 생성 클래스의 소스 아님
class GeneratedProxy extends Proxy implements UserMapper {
  User findById(Long id) {
    return (User) handler.invoke(this, findByIdMethod,
                                new Object[] { id });
  }
}

method는 이름 문자열이 아닌 java.lang.reflect.Method 객체입니다. 메서드의 반환 타입·파라미터·어노테이션을 조회할 수 있습니다. method.invoke(proxy, args)로 같은 프록시를 다시 호출하면 핸들러로 재진입하여 재귀가 발생합니다.

현재 Mapper는 SQL 어노테이션을 정확히 하나 요구합니다. 조회는 매핑 가능한 단건 객체 또는 List<T>, 변경은 int를 지원합니다. 인터페이스의 default 메서드는 자동 실행하지 않습니다.

실제 MyBatis와 어디가 다를까?

인터페이스·어노테이션·프록시로 SQL 호출을 연결한다는 아이디어가 대응합니다. simple-jorm은 호출할 때 어노테이션에서 SQL을 꺼내 자체 JdbcTemplate에 전달합니다. MyBatis는 설정 분석 과정에서 SQL 선언을 등록하고, 실행 시 MapperProxy·캐시된 메서드 실행기·SqlSession 등의 계층을 사용합니다. Spring의 JdbcTemplate을 거치는 구조가 아닙니다.

여기의 @Select는 com.jorm.mapper.Select입니다. MyBatis의 어노테이션과 별개이며, MyBatis 예제에서는 일반적으로 WHERE id = #{id}처럼 파라미터 매핑 문법을 사용합니다. XML 매핑·동적 SQL·복잡한 결과 매핑도 현재 구현 범위 밖입니다.

두 번의 SQL, 하나의 성공.

출금은 성공했는데 입금이 실패했습니다. 각 SQL이 따로 확정되면 돈이 사라집니다. 필요한 것은 메서드 하나의 편의보다, 업무 전체의 원자성입니다.

“같은 업무의 SQL이 같은 Connection을 쓰게 할 수 없을까?”

프로그램 방식 · 같은 관리자 인스턴스 주입
TransactionManager tx = new TransactionManager(source);
JdbcTemplate jdbc = new JdbcTemplate(tx);
AccountMapper accounts = MapperFactory.create(
  AccountMapper.class, jdbc);

tx.execute(() -> {
  accounts.withdraw(30, 1L);
  accounts.deposit(30, 2L);
  return null;
});
SAME THREAD + SAME MANAGER

연결은 프록시가 아닌 관리자가 기억한다.

ThreadLocal에 현재 스레드의 연결과 rollbackOnly 상태를 보관합니다. 같은 관리자에서 실행하는 JDBC 작업은 그 연결을 재사용합니다.

가장 바깥 경계에서 autoCommit을 끄고, 업무를 마친 뒤 commit 또는 rollback하고 상태와 연결을 정리합니다. 안쪽 REQUIRED 호출은 기존 트랜잭션에 참여합니다.

Service 프록시→ @Transactional 검사 →TransactionManager.execute→실제 Service→SQL들 · 같은 Connection

@Transactional은 이 경계를 선언하는 표시입니다. TransactionProxyFactory로 만든 프록시가 실제 Service 구현 메서드의 어노테이션을 읽고 업무를 감쌉니다. Mapper 프록시와 달리 호출할 target 객체가 있습니다.

INTERACTIVE 02 / PROXY BOUNDARY

같은 실패인데, 잔액이 다르다?

두 계좌는 각각 100에서 시작합니다. 출금 30은 성공하고, 입금은 잔액 상한 120 제약 때문에 실패합니다.

아래 정적 비교에서 세 호출 경로와 최종 잔액을 확인할 수 있습니다.
세 경로의 결과 · 정적으로 읽기
  1. 외부에서 transfer 호출: 프록시가 트랜잭션을 시작합니다. 입금 실패 시 출금까지 롤백하여 최종 잔액은 100 / 100입니다.
  2. 비트랜잭션 메서드에서 this.transfer: 자기 호출은 프록시로 재진입하지 않아 내부의 어노테이션을 검사하지 않습니다. 출금은 이미 자동 커밋되어 70 / 100이 남습니다.
  3. 트랜잭션이 있는 바깥 메서드에서 this.transfer: 자기 호출이 새 경계를 만들지는 않지만 이미 시작한 트랜잭션의 연결을 씁니다. 실패 시 함께 롤백되어 100 / 100입니다.

여기서 표시하는 실행 중 잔액은 해당 작업의 효과를 설명하는 값입니다. 다른 연결에서 미커밋 변경이 보인다는 의미는 아닙니다.

연결 공유 조건: 같은 스레드 + 같은 TransactionManager 인스턴스. 잔액 결과는 저장소의 TransactionSelfInvocationTest에 대응합니다.
REQUIRED와 rollbackOnly · 안쪽 예외를 잡아도 왜 롤백될까?

안쪽 execute() 또는 트랜잭션 Service 프록시가 기존 트랜잭션에 참여합니다. 그 참여 경계를 넘어 예외가 나오면 rollbackOnly를 기록합니다. 바깥 업무가 예외를 잡고 정상 반환해도 커밋할 수 없어 전체 롤백 후 UnexpectedRollbackException이 발생합니다.

반대로 같은 콜백 내부에서 예외를 잡아 경계 밖으로 보내지 않으면 관리자는 그 실패를 알 수 없습니다. 모든 catch가 무조건 전체 롤백을 만드는 것은 아닙니다.

new JdbcTemplate(dataSource)는 자체 관리자를 만듭니다. 별도로 만든 관리자의 트랜잭션과 자동으로 공유되지 않습니다. 다른 스레드·비동기 작업으로 연결을 전파하지도 않습니다.

실제 Spring 트랜잭션과 어디가 다를까?

프록시로 업무 경계를 감싸고 REQUIRED로 참여한다는 의미는 비슷합니다. 자체 Service 프록시는 구현 메서드의 표시만 읽으며 인터페이스 기반 JDK 프록시를 수동 생성합니다. Spring은 더 넓은 메타데이터 탐색·설정 기능과 클래스 기반 프록시도 제공합니다.

롤백 규칙은 다릅니다. 자체 구현은 SQLException과 checked 업무 예외도 롤백합니다. Spring의 기본 선언적 규칙은 RuntimeException·Error 중심이며 rollbackFor 등으로 바꿀 수 있습니다. Spring JDBC는 SQL 예외를 unchecked 예외로 변환한다는 점도 함께 봐야 합니다.

자체 구현은 REQUIRED만 지원합니다. REQUIRES_NEW·NESTED·savepoint는 없습니다. 자기 호출 우회는 Spring의 프록시 기반 AOP에서도 이해해야 하는 경계입니다.

이제 객체 구조가 SQL의 재료다.

테이블과 컬럼, ID가 정해지면 기본 CRUD의 형태는 반복됩니다. 이 정보를 객체에 적고, 공통 코드가 SQL을 만들게 했습니다.

매핑 선언 · 모두 com.jorm.entity의 자체 타입
@Table("users")
class User {
  @Id
  Long id;

  @Column("user_name")
  String name;

  User() {}
}
명시적 CRUD · 즉시 SQL 실행
User user = new User();
user.id = 1L;
user.name = "Alice";

int inserted = entities.persist(user);
User found = entities.find(User.class, 1L);
found.name = "Bob";
int updated = entities.update(found);
int deleted = entities.remove(found);
클래스·필드 어노테이션→EntityMetadata→SQL + 값 배열→JdbcTemplate → DB

EntityMetadata가 테이블명, ID 필드, 컬럼과 필드의 연결을 분석합니다. EntityManager는 클래스별 분석 결과를 캐시하고 객체의 값을 읽어 SQL을 생성합니다. 이 캐시는 클래스의 구조 정보를 재사용하며, 조회한 엔티티 객체를 보관하는 1차 캐시가 아닙니다.

호출생성하는 SQL의 형태현재 동작
persist(user)INSERT INTO users (id, user_name) VALUES (?, ?)즉시 실행, 변경 행 수 반환
find(User.class, id)SELECT id, user_name FROM users WHERE id = ?매번 조회·새 객체 생성, 없으면 null
update(user)UPDATE users SET user_name = ? WHERE id = ?ID 외 모든 매핑 필드 수정
remove(user)DELETE FROM users WHERE id = ?대상 없으면 0, 객체 값은 유지
생성 ID · IDENTITY와 UUID는 언제 값이 생길까?

직접 지정: 저장 전에 ID가 있어야 하고 INSERT에 포함합니다.

IDENTITY: @GeneratedValue(strategy = GenerationType.IDENTITY)를 붙이고 ID는 null로 둡니다. INSERT에서 ID를 제외하고 DB가 만든 키를 같은 연결에서 읽어 객체에 넣습니다. 자체 구현은 Long·Integer를 지원합니다.

UUID: INSERT 전에 UUID.randomUUID()로 값을 생성해 객체에 넣고 ID 컬럼도 함께 저장합니다. UUID·String 필드를 지원합니다.

생성 ID가 이미 있는 객체의 재저장은 거부합니다. 롤백되어 DB 행이 사라져도 객체에 넣은 ID는 남습니다. UUID는 SQL 실패 후에도 생성된 값이 남습니다. SEQUENCE·TABLE·AUTO 전략은 없습니다.

실제 JPA / Hibernate와 어디가 다를까?

객체·테이블 매핑과 SQL 생성은 ORM의 일부 역할입니다. JPA의 persist()는 엔티티를 영속성 컨텍스트의 관리 상태로 만드는 void API입니다. SQL 실행 시점은 flush·ID 전략 등에 영향을 받습니다. 자체 persist()는 즉시 INSERT하고 int를 반환합니다.

자체 find()는 매번 새 객체를 만듭니다. 필드만 수정해도 자동 UPDATE되지 않으며 명시적 update()가 필요합니다. JPA에서는 관리 상태 엔티티의 변경을 flush에서 동기화할 수 있고, JPA EntityManager에는 이와 같은 표준 update(entity) 메서드가 없습니다.

관계 매핑·복합 ID·상속 매핑·지연 로딩·영속성 컨텍스트는 아직 없습니다. 자체 @Table로 매핑 대상을 판단하고 JPA의 @Entity는 사용하지 않습니다. 메타데이터의 동시 접근 보장을 JPA EntityManager의 스레드 안전성으로 일반화해서도 안 됩니다.

학습은 순서대로 했지만, EntityManager가 Mapper를 거쳐 실행되지는 않습니다. 두 경로는 현재 함께 존재합니다.

조회한 객체의 상태까지 기억한다면.

SQL 자동 생성만으로 객체의 생명주기를 관리하게 되지는 않습니다. 현재 같은 ID를 두 번 조회하면 서로 다른 객체가 생기고, 값을 바꾸어도 명시적 수정 호출 전까지 DB는 바뀌지 않습니다.

현재 simple-jorm의 동작
User a = entities.find(User.class, 1L);
User b = entities.find(User.class, 1L);

// 행이 존재해도 a == b 는 false
a.name = "Bob";
// 아직 UPDATE하지 않았다.
entities.update(a); // 명시적으로 실행
NEXT QUESTIONS

앞으로 배울 세 가지

  1. 객체 동일성: 한 영속성 컨텍스트에서 같은 엔티티 ID를 같은 객체로 다루기.
  2. 변경 감지: 처음 상태와 현재 상태를 비교해 변경을 찾아내기.
  3. flush: 관리 중인 상태를 DB와 동기화하기. commit과 같은 작업은 아닙니다.
이 영역은 구현 완료 기능이 아닌 다음 학습 목표입니다. 실제 JPA도 모든 Java 객체의 변경을 무조건 저장하지 않습니다. 관리 상태·트랜잭션·flush 조건을 함께 이해해야 합니다.

SPECIFICATION & PROVIDER

JPA · Hibernate · EclipseLink

Jakarta Persistence(JPA)는 객체 영속화 표준입니다. Hibernate ORM과 EclipseLink는 이를 구현하는 provider입니다. 표준 API 의존성만으로는 실제 DB 작업을 수행할 수 없습니다.

애플리케이션 → JPA 구현체 → JDBC → DB
REPOSITORY ABSTRACTION

Spring Data JPA

JPA 기반 Repository 구현을 지원합니다. Hibernate와 서로 다른 계층으로 함께 쓸 수 있습니다. Repository 없이 EntityManager를 직접 사용하는 것도 가능합니다.

Repository → JPA provider → JDBC → DB
SQL-FIRST ACCESS

MyBatis · jOOQ · Spring JDBC

MyBatis는 직접 작성한 SQL과 Mapper를 연결합니다. jOOQ는 Java SQL DSL을 중심으로 실행·매핑도 제공합니다. Spring JDBC는 SQL 실행의 반복 절차를 줄입니다.

SQL·DSL·Mapper → 실행·매핑 → JDBC → DB
OTHER MODELS

Spring Data JDBC · R2DBC

Spring Data JDBC는 Aggregate 중심 저장 모델을 제공합니다. JPA식 영속성 컨텍스트·변경 감지를 전제로 하지 않습니다. R2DBC는 JDBC와 별도의 리액티브 연결 API 경로입니다.

SIDE NOTE / MAPPING COST

편해진 매핑에는 어떤 비용이 있을까?

리플렉션으로 반복 코드를 줄이면 실행 비용도 바뀝니다. 저장소에서는 행 수와 필드 수를 바꾸며 수동 매핑과 자동 매핑을 비교했습니다.

WHAT TO LEARN

측정 범위를 먼저 본다.

객체 변환만 측정할 때와 SQL 실행·전송까지 포함할 때 비율은 다를 수 있습니다. 행 수뿐 아니라 필드 수, 값 타입, 워밍업과 GC도 결과에 영향을 줍니다.

WHAT NOT TO GENERALIZE

프레임워크 전체 순위는 아니다.

2026-10-30의 로컬 MySQL 실험입니다. JMH나 운영 처리량 측정이 아니며, Spring·DbUtils 전체 파이프라인 비교도 아닙니다. 당시 매퍼와 현재의 조회별 준비 구현을 동일시하지 않습니다.

현재 코드의 prepare()는 컬럼과 필드의 연결을 조회별로 준비합니다. 과거 측정값을 이 변경 이후 성능의 증거로 사용하지 않습니다. 원본 보고서에서 환경·측정 구간·원시 결과와 한계를 함께 확인하세요.
